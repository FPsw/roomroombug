# roomroombug 프로젝트 설계도

> 개인용 투자 단말기. 매일 자동으로 데이터를 모으고, 내 매매를 복기하고, 내 조건에 맞는 종목을 찾아준다.
> 버전이 올라갈수록 데이터 규모를 의도적으로 키워서 **실제 데이터 병목을 만나고, 측정하고, 해결한 기록**을 남기는 것이 이 프로젝트의 두 번째 목표다.

작성일: 2026-11-13 · 이 문서는 Claude Code와 작업을 시작하기 위한 기준 문서다. 레포에는 `docs/DESIGN.md`로 둔다.

---

## 1. 프로젝트 원칙

1. **매일 쓰는 프로그램이어야 한다.** 사람 손 없이 매일 돌고, 내가 매일 연다.
2. **v0.x는 단순하고 정확하게, v1.0부터는 최대 성능을 지향한다.** 처음부터 최적화하지 않는다. 단순한 구현이 있어야 "얼마나 빨라졌는지" 비교할 기준선이 생긴다.
3. **최적화는 반드시 측정으로 시작해서 측정으로 끝난다.** 느낌으로 고치지 않는다. 전후 수치가 없는 최적화는 머지하지 않는다.
4. **핵심 로직은 직접 짠다.** `domain/`과 성능 개선 작업은 내가 구현하고, Claude Code는 리뷰·세팅·반복 코드를 맡는다.
5. **모든 큰 결정은 기록한다.** 설계 결정은 `docs/adr/`, 성능 개선은 `docs/perf/`.

## 3. UI 구성

다크 테마, 정보 밀도 높은 단말기 스타일. 마우스 없이 키보드만으로 대부분 조작할 수 있게 한다.

### 3.1 전체 레이아웃

```
┌──────────────────────────────────────────────────────────────────┐
│ roomroombug   [ Ctrl+K 종목·명령 검색 ]        마지막 수집 18:02 ● │  ← 상단 바
├────────┬─────────────────────────────────────────────────────────┤
│ 대시보드 │                                                         │
│ 복기    │                                                         │
│ 관심종목 │                     메인 영역                            │
│ 스크리너 │                  (화면별 패널 배치)                       │
│ 백테스트 │                                                         │
```

- 상단 바의 "마지막 수집" 표시는 항상 보인다. 수집 실패 시 빨간색.
- 모바일에서는 사이드바가 하단 탭으로 바뀐다.

## 4. 시스템 구조

```
[외부 데이터]            [Python 워커]              [DB]                [웹]
일봉·재무·공시·뉴스  →   수집 → 정규화 → 계산   →   Postgres   ←→   Next.js   ←   브라우저
거래내역 CSV ─────────────────────────────────────────────────────────┘ (업로드)
                              │
                              └→ 알림 (텔레그램/디스코드)
```

- 워커와 웹은 서로를 호출하지 않는다. **DB 테이블이 두 쪽의 계약**이다.
- 브라우저는 외부 금융 API를 직접 부르지 않는다. API 키는 워커와 서버에만 있다.
- 워커의 쓰기는 전부 upsert다. 같은 날짜를 다시 돌려도 결과가 같다.

- 원본(거래, 봉 데이터)과 계산 결과(라운드, 신호)를 분리한다. 계산 결과는 지우고 다시 만들 수 있어야 한다.

## 7. 성능 트랙: 버전별로 데이터를 키우고 병목을 푼다

### 7.1 진행 방식

버전마다 아래 순서를 반복한다.

1. **규모를 키운다**: 다음 버전의 데이터를 넣는다.
2. **측정한다**: 무엇이 얼마나 느린지 숫자로 잡는다.
3. **병목을 찾는다**: `EXPLAIN (ANALYZE, BUFFERS)`, 프로파일러로 원인을 특정한다.
4. **가설을 세우고 하나만 바꾼다**: 한 번에 한 가지.
5. **다시 측정한다**: 전후 비교.
6. **기록한다**: `docs/perf/NNNN-제목.md`에 보고서를 남긴다.

### 7.2 버전별 규모와 예상 병목

행 수는 계산값이고, 용량과 병목은 실제로 넣어본 뒤 확정한다.

| 버전 | 데이터 | 규모 | 예상 병목 | 써볼 기법 |
| --- | --- | --- | --- | --- |
| v0.x | 관심종목 일봉 | 50종목 × 10년 ≈ 12만 행 | 없음 (기준선 측정용) | 최적화하지 않는다 |
| v1.0 | 전 종목 일봉 10년 | 약 2,700종목 × 250일 × 10년 ≈ 675만 행 | 전 종목 스크리너 스캔, 백테스트 소요 시간, 대량 적재 속도, 스크리너 결과 표 렌더링 | 인덱스 설계, 실행 계획 분석, `COPY` 대량 적재, 지표 사전 계산 테이블, 물리화 뷰, pandas 벡터화 → Polars·DuckDB 비교, 표 가상 스크롤 |
| v2.0 | 분봉 | 100종목 ≈ 연 975만 행, 전 종목이면 최대 연 2.6억 행 (종목당 하루 390개 기준 상한) | 저장 용량, 시간 범위 조회, 분봉 차트 로딩, 집계 쿼리 | 월별 파티셔닝, BRIN 인덱스, TimescaleDB 하이퍼테이블·압축 비교, 오래된 데이터는 Parquet + DuckDB로 분리, 서버 측 봉 집계(1분→5분·60분), 차트 다운샘플링 |
| v3.0 | 실시간 체결 | 장중 연속 유입 | 수신 지연, 쓰기 폭주, 화면 갱신 과부하 | 버퍼링 후 배치 쓰기, 백프레셔, 최신가 인메모리 캐시(Redis), 서버→브라우저 push(SSE/WebSocket), 렌더 스로틀링 |

### 7.3 성능 목표 (초기값, 측정 후 조정)

| 대상 | 측정 항목 | 목표 |
| --- | --- | --- |
| 일일 수집 | 전 종목 일봉 하루치 적재 | 60초 이내 |
| 스크리너 | 전 종목 규칙 1개 평가 | 5초 이내 → v1.x에서 1초 이내 |
| 백테스트 | 전 종목 × 10년 × 규칙 1개 | 60초 이내 |
| 종목 차트 | 일봉 10년 로딩 (p95) | 300ms 이내 |
| 분봉 차트 | 1개월 분봉 로딩 (p95) | 500ms 이내 |
| 스크리너 표 | 2,700행 정렬·스크롤 | 끊김 없이 60fps |

### 7.6 v1.0에서 결정할 것: 대용량 저장소

Supabase 무료 플랜은 DB 500MB라 전 종목 10년 일봉부터 넘친다. v1.0을 시작할 때 아래 중 하나를 골라 ADR로 남긴다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. Supabase Pro (월 $25, 8GB) | 구조 변경 없음 | 분봉 단계에서 다시 부족, 확장 기능 제약 |
| B. 집 PC·보드에 Postgres 직접 운영 + 터널 | 비용 없음, 튜닝·운영을 전부 직접 경험, TimescaleDB 등 자유롭게 설치 | 가용성 직접 책임, 웹이 접근하려면 API 서버 필요 |
| C. 클라우드 VM (AWS 등) | 실무와 가장 비슷 | 비용 발생 |

B나 C를 고르면 웹과 대용량 DB 사이에 API 서버가 필요해진다. 이때 Spring Boot를 도입한다.
작은 서빙용 데이터(거래, 규칙, 신호, 관심종목)는 Supabase에 그대로 두고, 대용량 시계열만 분리하는 구성을 기본안으로 본다.

## 10. Claude Code 작업 규칙

`CLAUDE.md`에 그대로 옮겨 쓴다.

- 이 프로젝트의 기준 문서는 `docs/DESIGN.md`다. 구조나 스택을 바꾸려면 먼저 제안하고 승인받는다.
- `workers/src/rrb/domain/`의 구현은 사용자가 직접 작성한다. 이 폴더는 요청 없이 수정하지 않는다. 리뷰 요청을 받으면 문제점만 지적하고 코드를 고쳐 쓰지 않는다.
- 성능 개선 작업도 사용자가 직접 한다. 측정 스크립트 작성과 결과 해석 보조만 한다.
- 스키마 변경은 반드시 `supabase/migrations/`의 SQL 파일로 한다.
- 워커의 DB 쓰기는 upsert로 작성한다.
- 새 수집원은 `sources/` 어댑터로 추가하고, 기존 어댑터와 같은 형태의 표를 반환한다.
- 비밀값은 코드에 쓰지 않는다. `.env`와 `data/`는 커밋하지 않는다.
- 커밋은 Conventional Commits (`feat:`, `fix:`, `chore:`, `perf:`, `docs:`). 기능마다 브랜치 → PR.
- 새 라이브러리를 추가할 때는 이유를 PR 설명에 적는다.
- v0.x에서는 최적화하지 않는다. 읽기 쉽고 정확한 코드를 우선한다.
